[[adr-007]]
=== ADR-007: Message broker selection

Date:: 2026-03-02

Status:: Accepted

[.links]
owned-by:: <<sh-architect>>
uses-input:: <<in-007-cost>>, <<in-007-ops>>, <<in-007-throughput>>
addresses:: <<need-async-messaging>>
supersedes:: <<adr-004>>

[.triggers]
baseline:: 2026-03-02
on time.elapsed:: every P3M
on stakeholder.changed::
on alternative.emerged::

==== Context

We need a message broker for asynchronous communication between microservices. The broker must:

* Run on-premises (<<con-001>>)
* Handle 10,000+ messages per hour (<<rq-001>>)
* Be operationally simple for a small ops team

Alternatives evaluated: RabbitMQ, Apache Kafka, ActiveMQ Artemis.

Evaluation criteria and weights:

* [[in-007-cost]]**Cost** (licensing + hardware): weight 40% (<<sh-cfo>>)
* [[in-007-ops]]**Operability** (ease of operation, monitoring, recovery): weight 35% (<<sh-ops>>)
* [[in-007-throughput]]**Throughput**: weight 25% (<<sh-architect>>)

[.links]
|===
|Source |owned-by

|<<in-007-cost>> |<<sh-cfo>>
|<<in-007-ops>> |<<sh-ops>>
|<<in-007-throughput>> |<<sh-architect>>
|===

==== Decision

**RabbitMQ** was selected.

Scoring (weighted):

* RabbitMQ: 8.2
* Kafka: 7.5
* Artemis: 6.9

==== Consequences

* Operations team needs RabbitMQ training (1 week, budgeted).
* Clustering configured for high availability.
* Monitoring integrated with existing Prometheus stack.

[[section-technical-risks]]
== Risks and Technical Debts

* [[risk-001]]**Broker single point of failure**: If the message broker goes down, order processing halts.
  Mitigation: RabbitMQ clustering with automatic failover (in progress). Assessed 2026-05-01.

* [[risk-002]]**Overdue revisit rv-004 on ADR-007**: the NATS assessment was due 2026-10-03 and is still open on 2026-10-04.
  Impact: a better-suited broker could be missed. Mitigation: escalate to the architecture review board; close rv-004 by 2026-10-15.

* [[td-001]]**Hardcoded configuration**: Broker connection strings are hardcoded in multiple services.
  Remediation: move to a centralized config service (planned Q4 2026).
